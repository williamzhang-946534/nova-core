# 14. 决策与取舍

## ADR-001：采用模块化单体

**状态：** 建议

**背景：**

Nova 是个人开发的 Windows 本地系统，需要集成设备、AI、事件和 Web 控制台。第一阶段用户量只有一人，没有多实例部署需求。

**决策：**

所有后端模块运行在同一个 FastAPI 进程中，通过明确接口保持边界。

**理由：**

- 部署简单。
- 调试方便。
- 进程内调用延迟低。
- 维护成本适合个人开发。

**代价：**

- 单进程故障会影响所有模块。
- 需要自律避免模块互相随意引用。

**缓解：**

- 依赖注入。
- Repository 边界。
- 禁止 Agent 直接访问外部设备 API。
- 核心模块单元测试。

## ADR-002：后端选择 Python FastAPI

**状态：** 建议

**背景：**

用户熟悉 NestJS 和 Prisma，但 Python 在 AI Agent、结构化输出、模型适配和数据处理方面生态更成熟。

**决策：**

使用 Python + FastAPI。

**理由：**

- 异步 I/O 适合设备事件和模型调用。
- Pydantic 适合边界校验。
- 后续接入本地模型和数据处理生态更容易。
- OpenAPI 自动生成，便于前端协作。

**代价：**

- 用户 Python 后端经验较少。
- 需要遵守更严格的工程规范。

**缓解：**

- 使用类型标注。
- 保持简单分层。
- 核心模块先写接口和测试。

## ADR-003：第一阶段使用 SQLite

**状态：** 建议

**背景：**

第一阶段为单用户、单进程、本地运行，数据规模有限。

**决策：**

使用 SQLite 作为主数据库，未来可迁移 PostgreSQL。

**理由：**

- 零服务部署。
- 单文件备份。
- Windows 本地运行成本低。

**代价：**

- 写入并发有限。
- 不适合多进程高并发。

**缓解：**

- 短事务。
- Repository 隔离 SQL。
- 不使用 SQLite 特有 SQL。
- 统一 UUID 和 UTC 时间。

## ADR-004：事件系统使用应用内总线

**状态：** 建议

**背景：**

需要统一事件分发和持久化，但第一阶段没有跨服务投递需求。

**决策：**

使用应用内 Event Bus，事件写入 SQLite。

**理由：**

- 无额外部署成本。
- 延迟低。
- 足够支撑环境更新、自动化和 WebSocket。

**代价：**

- 进程崩溃时未入库事件可能丢失。
- 不支持跨进程消费。

**缓解：**

- 外部事件先入库再分发。
- 断线重连后只对配置范围内实体做当前状态对账，不回放完整历史。
- 未来需要时再评估外部队列。

## ADR-005：Home Assistant 作为第一阶段设备基础设施

**状态：** 建议

**背景：**

Home Assistant 已经提供设备集成、状态、控制、事件和协议兼容能力。Nova 不应重复建设这些能力。

**决策：**

通过 Home Assistant Adapter 接入设备。Nova 只保存轻量设备投影、别名、能力摘要和权限映射，不复刻 Home Assistant 的设备管理、发现、协议配置和完整历史。

**理由：**

- 降低第一阶段硬件和协议适配成本。
- 快速获得真实设备数据。
- 保持 Nova 与具体平台解耦。

**代价：**

- 依赖 Home Assistant 可用性。
- 需要维护适配层映射。

**缓解：**

- Device Adapter Interface。
- Device Registry 只保存 Nova 所需投影。
- Mock Adapter 用于离线测试。
- 未来可新增其他适配器。

## ADR-006：Agent 与 Tool Executor 分离

**状态：** 建议

**背景：**

AI 输出不可直接信任，真实设备操作需要权限、风险和结果验证。

**决策：**

Agent 只生成候选意图和计划，并提交给 Task System。Task System 编排执行，Tool System 通过领域服务和 Repository 完成业务处理，Device Adapter 独占外部设备通信，AI Provider 不接触数据库、任务状态和设备协议。

**理由：**

- 安全边界清晰。
- 便于审计。
- 便于测试。
- 支持更换模型。

**代价：**

- 执行链路更长。
- 需要维护工具注册和权限配置。

**缓解：**

- 第一阶段只实现少量工具。
- 工具 Schema 使用 Pydantic。
- 安全测试优先。
- 工程初始化时建立目录边界和 import 检查。

## ADR-007：统一 AI Provider 适配层

**状态：** 建议

**背景：**

项目初期可能使用 GLM、OpenAI-compatible 或其他模型，不能写死供应商。

**决策：**

业务代码只依赖 Provider Interface。

**理由：**

- 便于更换模型。
- 便于测试。
- 统一超时、错误和日志。

**代价：**

- 不同模型能力差异需要适配。

**缓解：**

- 结构化输出必须校验。
- Provider 声明能力。
- 不假设 GLM-5.3 完全等同 OpenAI。

## ADR-008：第一阶段不使用向量数据库

**状态：** 建议

**背景：**

记忆系统需要预留长期检索能力，但第一阶段数据量小。

**决策：**

使用结构化记忆表和关键词/时间检索。

**理由：**

- 降低部署复杂度。
- 避免过早优化。
- 便于用户查看和删除记忆。

**代价：**

- 语义检索能力弱。

**缓解：**

- MemoryStore 接口预留扩展。
- 重要记忆结构化保存。
- 未来可新增向量索引。

## ADR-009：Windows 原生运行

**状态：** 建议

**背景：**

第一阶段目标是个人电脑本地运行，优先降低调试和部署成本。

**决策：**

第一阶段 Windows 原生运行，不使用 Docker。

**理由：**

- 文件路径和网络访问简单。
- 调试体验好。
- Home Assistant 连接配置少。

**代价：**

- 环境隔离较弱。
- 复制部署不如容器一致。

**缓解：**
- 使用虚拟环境。
- 固定依赖版本。
- 提供启动脚本。
- 系统稳定后再评估 Docker。

## ADR-010：第一阶段不做多 Agent

**状态：** 建议

**背景：**

多 Agent 会增加状态管理、调试和安全难度。

**决策：**

使用单 Agent Runtime 加工具系统。

**理由：**
- 第一阶段目标是一条可靠闭环。
- 单 Agent 更容易测试和审计。

**代价：**

复杂并行任务能力弱。

**缓解：**

任务系统支持多步骤。
未来如确需再扩展。

## ADR-011：老人监护方向取消

**状态：** 已确认

**背景：**

用户明确取消老人监护相关产品方向。

**决策：**

Nova 当前和第一阶段均不开发老人监护、异常检测、养老、安全告警、远程照护和相关商业服务。

**影响：**

文档、需求、测试和实现中不得默认包含这些能力。

## ADR-012：API 使用单用户本地 Token

**状态：** 建议

**背景：**

第一阶段只有一个用户，但控制台具备设备操作能力。

**决策：**

使用环境变量配置 Bearer Token，除健康检查外 API 必须认证。

**理由：**

- 实现简单。
- 比无认证安全。
- 避免过早设计多用户系统。

**代价：**

不支持多角色和权限隔离。

**缓解：**

默认绑定 `127.0.0.1`。
所有设备操作仍经过权限系统。
未来可扩展用户体系。

## ADR-013：机器人不进入当前架构

**状态：** 建议

**背景：**

机器人会引入高风险物理动作、空间安全、紧急停止和硬件运维问题，与第一阶段的个人环境感知与低风险控制闭环不匹配。

**决策：**

当前模块清单、Device Adapter 设计、数据模型和路线图均不包含机器人模块、表结构或接口要求。机器人只保留在未来扩展文档中作为评估方向。

**重新评估前提：**

1. 第一阶段核心闭环稳定。
2. 高风险安全策略成熟。
3. 硬件形态和任务边界明确。
4. 已完成独立机器人架构与安全设计。

**代价：**

未来接入机器人时需要重新设计动作模型、测试策略和紧急停止机制，不能把普通设备接口直接扩展成机器人接口。

## 架构审查

| 审查项 | 结论 |
| --- | --- |
| 是否重复实现 Home Assistant | 否，设备注册表是轻量投影，自动化仅限 Nova 上下文场景 |
| 是否过度依赖 Home Assistant | 否，有适配层和轻量内部投影 |
| AI、设备控制和数据库是否耦合 | 否，分别通过 Provider、Adapter 和 Repository 隔离 |
| 是否有独立设备适配层 | 是 |
| 是否有环境状态模型 | 是 |
| 是否有事件系统 | 是 |
| 是否有任务执行记录 | 是 |
| 是否有权限控制 | 是 |
| 是否有执行结果验证 | 是 |
| 是否过度设计机器人能力 | 否，当前架构没有机器人模块或预留接口 |
| 是否引入不必要数据库或消息队列 | 否 |
| 是否个人可维护 | 是 |
| 是否可在 Windows 本地运行 | 是 |
| 是否可控制在 1000 元内 | 是 |
| 是否可逐步接入传感器 | 是 |
| 是否可更换 AI 模型 | 是 |
| 是否可更换设备平台 | 是 |
| 是否可扩展语音、视觉、机器人 | 仅保留未来评估方向，不提前设计接口 |

## 主要风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| Python 经验较少 | 开发速度波动 | 类型标注、测试、小步实现 |
| Home Assistant API 差异 | 设备同步失败 | 适配层、Mock、健康检查 |
| 模型输出不稳定 | 工具调用失败 | 结构化输出、校验、重试限制 |
| 设备状态延迟 | 验证误判 | 等待后重读、验证超时 |
| SQLite 写入并发 | 事件处理阻塞 | 短事务、批量优化 |
| 安全配置错误 | 误操作设备 | 默认拒绝、安全测试 |
| 范围蔓延 | 第一阶段无法完成 | 明确不开发清单 |

## 重新评估触发条件

以下情况出现时，应重新评估对应决策：

1. SQLite 查询或写入成为瓶颈：评估 PostgreSQL。
2. 需要跨进程事件消费：评估持久队列。
3. 多用户访问成为需求：扩展用户和角色。
4. 部署到多台机器：评估容器化。
5. 记忆语义检索明显不足：评估向量索引。
6. 需要并行复杂任务：评估更完整任务编排。
7. 接入机器人：先满足 ADR-013 的重新评估前提，再设计高风险工具和安全策略。
