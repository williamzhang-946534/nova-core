# 15. 未来扩展

## 扩展原则

1. 未来能力进入开发前，先定义接口和安全边界。
2. 未来能力不得破坏第一阶段核心闭环。
3. 每个扩展必须有明确阶段目标。
4. 高风险能力必须先补安全策略和测试。
5. 不为了“未来可能用到”提前引入复杂基础设施。
6. 未来评估问题不自动变成当前模块、表结构或接口要求。

## 扩展点

| 扩展点 | 位置 | 当前状态 |
| --- | --- | --- |
| 设备平台 | Device Adapter Interface | 第一阶段仅 Home Assistant / Mock，不包含机器人 |
| AI 模型 | AI Provider Interface | 已设计 |
| 事件类型 | Event Schema | 已设计 |
| 工具能力 | Tool Registry | 已设计 |
| 记忆检索 | MemoryStore | 已设计 |
| 自动化动作 | Automation Action Model | 仅限少量 Nova 上下文规则，不做通用动作平台 |
| 前端页面 | Frontend Dashboard | 已设计 |
| 数据库 | Persistence Layer | 已设计 |
| 语音交互 | Future Extension | 仅文档记录，未设计当前模块 |
| 视觉感知 | Future Extension | 仅文档记录，未设计当前模块 |
| 机器人 | Future Extension | 仅保留独立安全评估方向 |

## 1. 更多设备适配器

### MQTT Adapter

适用：

- ESP32 自制传感器
- 自定义执行器
- 局域网设备

必须新增：

- Topic 到设备的映射
- Payload Schema
- 设备能力声明
- 在线判定策略
- 安全风险等级

### ESP32 传感器

推荐通过 MQTT 接入，而不是为每个硬件单独写适配器。

传感器数据进入：

```text
MQTT Adapter
→ DeviceState
→ sensor_updated event
→ Environment Context
```

### 机器人评估

机器人不能作为普通设备直接接入，当前 Device Adapter Interface 中也不预留 Robot Adapter。未来进入评估时必须先定义：

- 紧急停止
- 动作风险
- 空间限制
- 人工确认
- 执行验证
- 失败回退

在安全策略成熟前，不实现机器人控制。

## 2. 语音交互

未来可新增：

- 语音输入
- 语音输出
- 唤醒词
- 本地或云端 ASR/TTS Provider

新增模块边界：

```text
Voice Input
→ Transcription Provider
→ Agent Runtime
→ Task System
→ Voice Output Provider
```

必须处理：

- 录音授权
- 音频数据保留
- 误唤醒
- 语音命令确认
- 高风险命令拒绝

## 3. 视觉感知

未来可新增视觉 Provider 和视觉事件：

- 人员在场
- 物体状态
- 空间变化
- 设备面板状态

约束：

1. 不做完整视频监控系统。
2. 不默认保存原始视频。
3. 图像事件必须可关闭。
4. 敏感视觉数据必须显式授权。
5. 视觉结论只能作为事件或上下文，不能直接触发高风险动作。

## 4. 本地 AI 模型

可通过新增 Provider 实现：

```text
Agent Runtime
→ AI Provider Interface
→ Local Model Provider
```

需要评估：

- Windows GPU/CPU 能力
- 模型加载时间
- 内存占用
- 结构化输出能力
- 工具调用能力
- 超时策略

本地模型不能绕过 Tool System 和 Safety Policy。

## 5. PostgreSQL

迁移触发条件：

- 数据量超过 SQLite 舒适范围
- 需要多进程写入
- 需要更复杂查询
- 需要长期服务化部署

迁移前必须保持：

- Repository 边界
- 无 SQLite 方言
- UUID 主键
- UTC 时间
- JSON 结构校验

## 6. 外部消息系统

触发条件：

- 需要跨进程事件消费
- 需要严格投递保证
- 需要事件回放

可选路径：

- 先实现数据库事件回放
- 再评估轻量队列
- 最后才考虑 Kafka 或 RabbitMQ

第一阶段不引入。

## 7. 多用户与权限

当前单用户。未来如需要多用户，应新增：

- 用户表
- 角色表
- 设备权限组
- 工具权限组
- 审计查询

必须在多用户前重新审查：

- 设备控制权限
- 记忆隔离
- API Token 生命周期
- 通知归属

## 8. 插件系统

当前不做插件市场。

如果未来需要插件化，应满足：

- 独立权限声明
- 风险等级声明
- 输入输出 Schema
- 版本管理
- 禁用和卸载
- 审计日志

在安全模型成熟前，插件系统会显著增加攻击面。

## 9. 机器人与具身智能

以下内容只是未来评估问题，不形成当前架构模块、表结构或接口要求。未来方向可以保留，但必须分阶段：

1. 只读环境感知。
2. 低风险动作。
3. 人工确认动作。
4. 受限空间任务。
5. 更复杂的自主任务。

每一阶段都必须有：

- 安全测试
- 紧急停止
- 失败回退
- 任务边界
- 人工监督策略

## 10. 复杂任务规划

第一阶段只支持简单单步和多步任务。

未来可扩展：

- 任务模板
- 条件分支
- 并行步骤
- 失败重规划
- 长任务恢复

扩展前提：

- Task 状态机稳定
- 工具执行可靠
- 结果验证可靠
- 权限模型成熟

## 11. 移动端与远程访问

当前不做远程访问。

未来如需要，应先设计：

- HTTPS
- 强认证
- 设备操作二次确认
- 审计日志
- 远程访问开关
- 风险限制

远程访问会显著提高安全要求，不能只做端口转发。

## 12. 部署扩展

当前推荐 Windows 原生运行。

未来可选：

1. Windows 服务
2. Docker Compose
3. NAS 部署
4. 小型主机部署

触发条件：

- 系统需要长期无人值守运行
- 需要自动重启
- 需要跨机器复制

## 不应提前实现的内容

| 功能 | 原因 |
| --- | --- |
| 自研 Zigbee/Matter 协议 | Home Assistant 已提供，成本极高 |
| 完整视频监控 | 超出当前产品边界 |
| 多 Agent 框架 | 增加复杂度且无必要 |
| 插件市场 | 安全和治理成本高 |
| 多租户 SaaS | 超出个人系统定位 |
| 高风险自主控制 | 安全模型未成熟 |
| 向量数据库 | 当前记忆规模不需要 |
| Kubernetes | 单机项目运维成本过高 |

## 未来扩展流程

每个未来功能进入开发前，必须补充：

1. 产品目标
2. 安全边界
3. 数据模型变更
4. API 影响
5. 测试策略
6. 隐私影响
7. 维护成本
8. 是否需要用户确认

## 结论

Nova Core 的扩展能力来自清晰的接口边界，而不是提前堆叠复杂基础设施。第一阶段应把设备抽象、事件、任务、工具安全执行和验证闭环做稳定，再评估 MQTT、语音、视觉、本地模型和机器人方向。
