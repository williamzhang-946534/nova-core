# 01. 产品定义

## 产品定位

Nova Core 是个人 AI 环境感知与智能控制系统。它连接真实环境中的设备和传感器，理解当前状态与用户目标，规划任务，通过受控工具执行，并验证和记录执行结果。

Nova Core 的关键区别不是“能聊天”，而是能将自然语言目标转化为可审计、可验证、受权限约束的真实世界操作。

```text
用户目标
→ 环境感知
→ 意图理解
→ 任务规划
→ 工具选择
→ 权限与风险检查
→ 设备执行
→ 状态验证
→ 任务记录
```

## 目标用户

第一阶段的唯一目标用户是系统开发者本人，即拥有 Windows 电脑、Home Assistant 环境和一定前后端开发能力的个人开发者。

用户画像特点：

- 熟悉 React、TypeScript、Ant Design、NestJS 和 Prisma。
- Python 后端经验相对较少，但愿意使用适合 AI Agent 开发的生态。
- 希望在个人电脑上运行完整系统。
- 初期预算控制在 1000 元人民币以内。
- 希望项目能逐步形成自己的核心技术，而不是只做一个模型供应商示例。

## 用户价值

### 1. 环境可理解

用户可以用自然语言询问家中或系统中的状态，例如：

- “现在客厅温度多少？”
- “哪些设备在线？”
- “刚才有什么变化？”
- “今天有没有自动任务执行失败？”

Nova 不是简单转发 Home Assistant 查询，而是将设备状态、事件、区域、用户目标和任务历史组织成自己的环境上下文。

### 2. 目标可执行

用户可以提出目标，例如：

- “把客厅灯打开。”
- “如果温度超过 28 度，提醒我。”
- “检查一下设备状态，告诉我有没有异常。”

Nova 将目标解析为任务计划，通过工具执行，并把执行过程和结果展示给用户。

### 3. 执行可验证

设备控制后，Nova 会读取设备实际状态，与预期结果对比，记录：

- 执行前状态
- 预期状态
- 实际状态
- 是否验证成功
- 错误信息
- 相关事件和任务步骤

### 4. 过程可追溯

每一次重要操作都会形成记录，用户可以在 Web 控制台查看：

- AI 对话
- 任务计划
- 工具调用
- 权限判断
- 执行结果
- 设备事件
- 自动化触发记录

### 5. 偏好可积累

Nova 能区分实时状态、事件历史、用户偏好和长期经验。它不会把所有聊天记录直接当成长期记忆，而是通过结构化接口保存有价值的偏好和任务经验。

## 第一阶段产品能力

### 必须具备

1. 连接 Home Assistant。
2. 同步设备列表和设备能力。
3. 读取设备当前状态。
4. 订阅设备状态变化事件。
5. 建立环境状态模型。
6. 保存事件、任务、工具调用和对话记录。
7. 提供自然语言对话入口。
8. 查询设备、环境和事件。
9. 执行低风险设备控制。
10. 控制后验证设备状态。
11. 提供系统概览、设备列表、事件时间线、任务记录和对话页面。
12. 支持少量 Nova 上下文通知规则和经确认的低风险动作规则。
13. 支持通过配置更换 AI 模型。
14. 支持通过 Mock Device Adapter 测试完整流程。

### 可以后置

- 复杂自动化编排
- 高级记忆检索
- 向量数据库

- 视觉感知

## 核心场景

### 场景 1：环境查询

**输入：** 用户询问“现在家里有什么设备开着？”

**过程：**

1. Agent 解析意图为只读查询。
2. Agent 调用查询环境状态或设备列表工具。
3. Tool Executor 校验工具权限。
4. 系统从 Device Registry 和 Environment Context 获取状态。
5. Agent 汇总结果并返回。

**输出：** 当前开启设备列表、区域和状态摘要。

**验收：** 不修改任何设备状态，响应中包含真实设备数据，并留下查询日志。

### 场景 2：低风险设备控制

**输入：** 用户要求“打开客厅灯”。

**过程：**

1. Agent 识别目标设备与动作。
2. Task Planner 生成单步任务计划。
3. Safety Policy 判定风险等级为低风险。
4. Tool Executor 校验参数与权限。
5. Device Adapter 调用 Home Assistant。
6. 系统读取设备状态并验证结果。
7. Task System 记录执行过程。

**输出：** 控制成功或失败，以及验证结果。

**验收：** 实际设备状态发生变化，任务历史可查询，失败时有明确错误。

### 场景 3：状态变化感知

**输入：** Home Assistant 上报设备状态变化。

**过程：**

1. Device Adapter 标准化事件。
2. Event System 持久化事件。
3. Environment Context 更新当前状态。
4. 自动化引擎判断是否有规则满足。
5. 如满足则触发任务或通知。

**输出：** 环境状态更新、事件时间线记录和可能的自动化执行。

**验收：** 事件不丢失，刷新页面后仍可查看历史。

### 场景 4：任务失败处理

**输入：** 用户要求控制设备，但设备离线。

**过程：**

1. Device Adapter 返回设备不可用错误。
2. Tool Executor 包装错误并记录工具调用结果。
3. Task System 将任务置为失败。
4. Event System 写入任务失败事件。
5. Agent 向用户说明失败原因。

**输出：** 明确的失败原因和可追溯的任务记录。

**验收：** 系统不崩溃，不显示成功，错误信息可定位。

## 产品成功标准

第一阶段成功必须同时满足：

1. Nova 可以在 Windows 本地启动。
2. Web 控制台可以访问后端。
3. 可以连接真实 Home Assistant。
4. 可以读取真实设备列表和状态。
5. 可以记录设备状态变化事件。
6. 用户可以通过自然语言查询设备。
7. 可以控制一个低风险设备。
8. 控制后可以验证实际状态。
9. 任务执行历史完整。
10. 设备离线或 API 超时时能正确报告错误。
11. 没有真实设备时，Mock Device Adapter 可以跑通核心流程。
12. API Key 不出现在源码中。

## 与 Home Assistant 的关系

Home Assistant 是第一阶段的设备基础设施，负责：

- 设备集成
- 设备发现
- 实体管理
- 设备状态
- 设备控制
- 状态事件
- 设备历史
- 协议适配
- 基础自动化
- 智能家居生态兼容

Nova Core 不重复建设这些能力。Nova 负责：

- 环境语义化
- 事件关联
- 用户意图理解
- 任务规划
- 工具权限
- 多设备编排
- 执行验证
- 记忆与偏好
- AI 自动化规划

Home Assistant 的实体 ID、状态字符串和服务调用格式不能直接泄漏到 Agent 或业务核心中，必须经过 Device Adapter 和 Device Registry 转换。

### 避免重复建设的边界

| 能力 | 归属 | 说明 |
| --- | --- | --- |
| 设备发现和协议适配 | Home Assistant | Nova 不自研 Zigbee、Matter 或设备集成层 |
| 完整设备注册信息 | Home Assistant | Nova 只保存设备投影、别名、能力摘要和权限 |
| 完整设备历史 | Home Assistant | Nova 只保存上下文、任务和审计所需事件 |
| 普通定时和简单自动化 | Home Assistant 优先 | Nova 不做通用自动化编辑器或场景系统 |
| 需要 AI 上下文的自动化 | Nova | 例如结合用户偏好、任务历史、多设备状态生成计划 |
| 任务执行审计 | Nova | 记录计划、工具调用、验证结果和用户确认 |

Nova 的自动化第一阶段只做通知型和经确认的低风险动作型规则，不做复杂编排，也不替代 Home Assistant 自动化。

## 产品边界结论

第一阶段应做一个窄而完整的个人系统：只接入 Home Assistant，只做必要的 Web 控制台，只开放低风险设备控制，但完整实现状态感知、事件记录、任务执行、结果验证和审计日志。

复杂能力不提前实现，只通过设备适配接口、事件格式、任务模型和工具权限模型预留扩展空间。
